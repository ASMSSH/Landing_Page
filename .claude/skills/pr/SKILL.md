# PR 생성 (pr)

브랜치당 PR 하나. **앞 대화에 의존하지 않는다** — 무엇을 했는지는 전부 git에서 복원한다.

## 1. 컨텍스트 복원

```bash
git branch --show-current
git fetch origin dev
git log origin/dev..HEAD --oneline
git diff origin/dev...HEAD --stat
git diff origin/dev...HEAD
```

- `dev`·`main`이면 중단한다.
- 푸시 안 된 커밋이 있으면 먼저 푸시한다.
- 커밋 메시지만 보고 요약하지 말고 **diff를 직접 읽는다.** PR 본문의 정확도가 여기서 갈린다.
- `docs/spec/SSH-<번호>/spec.md`·`tasks.md`가 있으면 읽는다 — 본문의 「왜」는 거기서 온다.

## 2. 범위 체크

**줄 수는 보지 않는다.** 보는 것은 하나다 — **이 변경이 전부 그 티켓 때문에 생긴 것인가.**

1. 브랜치명에서 이슈 키를 뽑아 `mcp__atlassian__getJiraIssue`로 티켓을 읽는다
2. `--stat`의 파일 목록을 훑는다
3. **파일마다 "이게 왜 이 티켓에 필요한가"를 한 줄로 답한다**
4. 답이 안 나오는 파일이 범위 밖이다

| | 예시 |
| --- | --- |
| **범위 안** | 라우팅 분기, `sitemap.xml` 등록, 그 작업 때문에 생긴 lint·타입 수정, `.env.example` 이름 추가 |
| **범위 밖** | 눈에 띄어서 고친 무관한 버그, 요청 없던 리팩터링, "하는 김에" 정리 |

범위 밖으로 판정한 게 있으면 **PR을 만들기 전에 사용자에게 알린다.** 뺄지, 별도 PR로 낼지는 사용자가 정한다.

### 나눌 수 있었는지 본다

범위가 맞아도 **독립적으로 쓸 수 있는 사용자 행동 여럿**이 한 PR에 들어 있으면 알린다. 이미 다 만든 뒤라
**나누라고 하지 않는다** — "이번은 이대로 내고 다음부터 티켓을 쪼개자"도 정상적인 답이다. 사용자가 정한다.

## 2-a. Draft냐 본문 갱신이냐

**사람 리뷰는 두 번이다.** Draft(1차: 작업 계획) → 개발 → 본문 갱신 + `/pr-review` → 사람이 Ready로(2차: 결과물).

```bash
gh pr list --head "$(git branch --show-current)" --state all --json number,isDraft,state,url
```

| 상황 | 조건 | 동작 |
| --- | --- | --- |
| **Draft 생성** | 열린 PR 없음 + 변경이 `docs/`·문서·설정뿐 | `gh pr create --draft --base dev` |
| **본문 갱신** | 이미 Draft PR이 있고 코드가 추가됨 | `gh pr edit`로 본문만 갱신. **Draft로 둔다** |
| **바로 Ready** | 열린 PR 없음 + 코드 포함 | `gh pr create --base dev` — 1차 리뷰를 건너뛴 경우다. 왜 그랬는지 보고에 적는다 |

### 리뷰를 요청하는 전환은 내가 하지 않는다

**`gh pr ready`도, Jira 진행 중 → 검토 중도 사람이 한다.** "이제 남이 시간을 써서 봐도 된다"는 선언이고
그 판단은 만든 사람이 내린다. Jira 검토 중은 Slack으로 자동 발송된다.

**Draft로 만든 뒤에는 멈춘다.** 1차 리뷰를 기다리고, 이어서 개발하지 않는다. 보고에 "1차 리뷰 대기"를 명시한다.

**본문 갱신 시**에는 `✨ 세부 내용`을 문서 요약에서 **실제 구현 내용으로 바꾸고**, 1차 리뷰 지적을 어떻게 반영했는지
`📍 PR Point`에 적는다.

**UI가 바뀐 PR은 스크린샷 3장(1440 · 768 · 390)이 다 있어야 Ready로 갈 수 있다.** 한 장이라도 없으면
무엇이 없는지 보고에 적고 Ready 전환을 권하지 않는다 → [5. 스크린샷](#5-스크린샷)

## 2-b. 본문을 갱신했으면 `/pr-review`까지 돌린다

**개발이 끝난 PR(「본문 갱신」·「바로 Ready」)은 여기서 끝내지 않는다.** 본문 갱신 → `/pr-review` → 지적 반영 → 보고.
**이게 에이전트의 마지막 일이다.** Draft를 처음 만든 경우(문서만)는 돌리지 않는다.

**순서를 지킨다 — 본문을 먼저 갱신하고 그다음 리뷰를 돌린다.** 리뷰어는 PR 본문도 읽는다. 낡은 본문인 채로
돌리면 이미 해소된 것을 지적으로 받아 적게 된다.

- **반드시 별도 서브에이전트로 돌린다.** `pr-review` 스킬이 그 규칙을 들고 있다
- 지적은 **등급대로 처리한다.** 안 고친 것은 이유를 적는다
- 반영한 내용은 `📍 PR Point`에도 남긴다

## 3. 제목

```
작업한 내용(SSH-번호)
```

스코프는 없다 — 스택이 하나다. 브랜치명 `<type>/SSH-<번호>`에서 이슈 키를 뽑고, Jira 제목을 그대로 베끼지 말고
**실제로 한 일**을 쓴다. 예) `/apply 진입점 + 페이지 셸 구성(SSH-542)`

> Squash Merge하면 이 제목이 그대로 `dev`의 커밋 제목이 된다. 규칙 CI가 `(SSH-번호)` 접미사와 브랜치 키 일치를 검사한다.

## 4. 본문 — 저 문맥(Low Context) 원칙

**읽는 사람이 사전 지식 없이 이 PR에 들어온다고 가정한다.** 6개월 뒤의 나는 지금 아는 걸 하나도 기억 못 한다.

본문에 반드시 들어가야 할 것:

1. **왜 만드는가** — Jira 이슈, `docs/spec/`의 해당 문서
2. **어떻게 구현했는가** — 접근. 상태 → 컴포넌트 → 스타일 → 연결 중 어디를 어떻게
3. **이번 PR의 변경점**
4. **화면** — UI 작업이면 스크린샷 3장 + Vercel 프리뷰 링크
5. **무엇을 테스트했는가 / 해야 하는가**

`.github/pull_request_template.md`의 5섹션에 녹여 넣는다. **`🙋 남기는 말`을 뺀 나머지에 빈 섹션을 남기지 않는다.**

### `🙋 남기는 말`은 채우지 않는다

**이 칸만은 비워서 올린다.** 사람이 직접 쓰는 자리다. 초안도 넣지 않는다 — 초안이 있으면 사람은 대개 고치지 않고
그대로 두고, 그러면 사람 말이 아니라 도구 말이 남는다. 빈 칸은 "없음"으로 읽는다.
보고에 **"`🙋 남기는 말`은 비워뒀습니다"**라고 적는다.

### 사람처럼 쓴다

PR 본문은 보고서가 아니라 **팀원에게 남기는 인수인계 메모**다. 기준은 실제 팀원들의 PR이다.

- **바로 본론.** 배경·목적 문단 없이 "요약 레일 진료비 NaN 뜨던 거 고쳤습니다"부터.
- **어미를 섞는다.** `~했습니다` / `~입니다!` / `~더라구요` / 명사형 끝. 균일하면 기계 티가 난다.
- **팀원의 단어로.** "꼬이는 부분", "짜잘한", "일단 ~로 해뒀습니다". 보고서 상투구("본 PR에서는", "~를 통해",
  "안정성을 높였습니다", "다음과 같습니다")가 나오면 말로 할 표현으로 바꾼다.
- **불확실을 그대로 노출.** "~할지 고민 중입니다. 의견 주세요!"
- **꾸밈은 최소.** 본문 볼드는 0~2번, 표는 스크린샷 배치에만. 불릿을 병렬로 맞추려 하지 않는다.
- **사소한 변경들은 `## 짜잘한 변경` 하나로 묶는다.** 전부 나열된 변경 목록이 가장 큰 AI 신호다.
  단, 저 문맥 원칙은 지킨다 — 줄이는 건 설명의 밀도지 기록할 사실이 아니다. 긴 근거는 토글로 접는다.

오타를 일부러 만들지는 않는다. **본문을 완성하면 이 기준으로 한 번 훑고 고친 뒤에 올린다.**

### 긴 내용은 토글로 접는다

줄글 5줄 초과 · 코드 15줄 초과 · 의사결정의 근거·대안·시행착오 전체 → `<details>`. 코드블록 앞뒤 빈 줄 필수.

```markdown
<details><summary>원인 확인 과정 (Vercel rewrite 순서)</summary>
<p>

내용

</p>
</details>
```

**제목 단계를 지킨다.** 템플릿의 5개 섹션은 `#`, 소제목 `##`, 더 아래 `###`. 섹션 사이 여백은 `<br><br>`.
**`---`를 넣지 않는다** — GitHub이 `#`에 이미 밑줄을 그린다.

섹션별로:

**📌 관련 이슈** — `Jira: SSH-542`. `docs/spec/SSH-542/spec.md`, 참고한 위키 문서 이름.

**🙋 남기는 말** — **비워둔다.**

**📍 PR Point** — 비우지 않는 게 중요하다. 결정 하나마다 `## 소제목`: 문제 상황 1~3줄 → 근거·대안은 토글 → 선택과 이유 →
남은 고민은 "~할지 고민 중입니다"로 질문. 검증 내역은 체크박스(`- [x] npm test 통과`, 못 한 것은 `- [ ]`).
**타협한 곳**("if 문 하나로 때웠다")은 여기 적는다 — 적으면 부채고 안 적으면 사고다. 미룬 것은 Jira 티켓 링크.

**✨ 세부 내용** — 커밋 나열이 아니라 **리뷰어가 읽을 변경 요약**. 접근 → 레이어별 3~6줄.
```
- /apply 상태를 useReducer 하나로 (state.ts, node:test 8건)
- 셸 컴포넌트 7개 — 헤더·프로그레스·레일·액션 행·푸터
- 768 이하 1열, 480 이하 프로그레스 압축
- vercel.json SPA rewrite (api/ 제외)
```

**📸 스크린샷** — 아래 5절.

## 5. 스크린샷

`git diff --stat`에 `Project/src/**/*.tsx`나 `Project/src/**/*.css`가 있으면 필요하다. 서버리스·문서 PR이면 건너뛴다.

**웹 업로드(드래그)는 쓰지 않는다.** 스크린샷은 검증 기록으로 `docs/spec/SSH-<번호>/`에 커밋하고
**그 blob URL을 본문에 임베드**한다 — 캡처부터 첨부까지 전부 내 몫이다.

### 몇 장을 찍나 — 대표 상태는 3장이다

| 무엇 | 몇 장 |
| --- | --- |
| **대표 상태** (화면에 들어갔을 때 처음 보이는 모습) | **1440 · 768 · 390 폭 3장** |
| 나머지 상태 (로딩·실패·빈 상태·모달 열림 …) | 1440 한 장씩 |

**390(모바일)은 예외가 없다.** 데스크톱에서만 보고 머지하면 모바일이 깨진 걸 사용자가 먼저 본다.
못 찍었으면 무엇이 없는지 보고에 적는다.

파일명: `docs/spec/SSH-<번호>/<화면>-<폭>.png` (예: `apply-shell-1440.png`, `apply-shell-390.png`).

### 캡처 — gstack browse(헤드리스 Chromium)

dev 서버를 띄우고 `$B`(gstack `browse` 바이너리)로 뷰포트를 바꿔 가며 찍는다. 명령 목록은 `/browse` 스킬에 있다.

```bash
B="$HOME/.claude/skills/gstack/browse/dist/browse"
(cd Project && npm run dev >/dev/null 2>&1 &)   # 이미 떠 있으면 생략. 포트는 vite 출력에서 확인
sleep 2
OUT=docs/spec/SSH-<번호>
$B goto http://localhost:5173/apply?r=test
$B viewport 1440x900 && $B screenshot "$OUT/apply-shell-1440.png"
$B viewport 768x1024 && $B screenshot "$OUT/apply-shell-768.png"
$B viewport 390x844  && $B screenshot "$OUT/apply-shell-390.png"
```

- `screenshot`은 기본이 full page다. 첫 화면만 필요하면 `--viewport`를 붙인다
- 찍은 뒤 Read 도구로 PNG를 한 번 열어 **내가 먼저 본다** — 빈 화면·깨진 레이아웃을 그대로 올리지 않는다
- Vercel 프리뷰가 있으면 로컬 대신 프리뷰 URL로 찍어도 된다 (`https://landing-page-git-<브랜치 slug>-ppaangss.vercel.app`).
  프리뷰는 새로고침·rewrite까지 검증되므로 그쪽이 더 좋다
- 헤드리스 Chromium이 없으면 `/browse` 스킬이 설치한다. 설치가 멈추면 사람에게 돌린다

### PR 본문 처리

- 캡처함 → `docs/spec/SSH-<번호>/`에 커밋(`docs: SSH-<번호> 검증 스크린샷 추가`)·푸시한 뒤 **blob URL로 임베드**
- 일부만 → 찍은 것은 임베드하고 `<!-- 스크린샷 필요 - <무엇이 빠졌나> -->` + Draft 유지
- UI 변경 없음 → `해당 없음`

임베드는 **커밋 SHA를 앵커로 한 blob URL + `?raw=true`**. PR head 커밋은 `refs/pull/<번호>/head`로 남아
브랜치를 지워도 깨지지 않는다. **브랜치명으로 앵커하지 마라.**

```markdown
프리뷰: https://landing-page-git-feat-ssh-543-ppaangss.vercel.app/apply?r=test

| 1440 | 768 | 390 |
| --- | --- | --- |
| <img src="https://github.com/ASMSSH/Landing_Page/blob/<SHA>/docs/spec/SSH-543/apply-s1-1440.png?raw=true" width="420"> | <img … width="260"> | <img … width="160"> |
```

### 마무리 — 렌더링을 확인시킨다

```bash
open <PR URL>
```

세 장이 표에서 실제로 렌더링되는지는 **사람이 눈으로 확인한다.** 보고에 "이미지 렌더링 확인해 주세요"를 남긴다.

## 6. 생성

라벨은 브랜치 type에 맞춘다(이 레포의 기존 라벨): `feat`→`⚒️ Feature`, `fix`→`🪚 Fix`, `chore`→`⚙️ chore`,
`docs`→`📜 docs`, `refactor`→`🪠 Refactor`, `style`→`✏️ Style`. 화면 작업이면 `🎨 Design`을 함께.

```bash
# Draft 생성 (문서만 있을 때)
gh pr create --draft --base dev --title "<제목>" --body-file <본문파일> --label "<라벨>"

# 바로 Ready (코드 포함, 1차 리뷰를 건너뛴 경우)
gh pr create --base dev --title "<제목>" --body-file <본문파일> --label "<라벨>"

# 이미 있는 Draft에 내용이 추가됐을 때 — 본문만 갱신한다
gh pr edit <번호> --body-file <본문파일>
```

- 본문은 임시 파일(저장소 밖)로 넘긴다. 인라인 문자열은 줄바꿈이 깨진다
- **PR 본문에 AI 서명·생성 표시를 넣지 않는다.** CI가 막는다
- **`gh pr ready`를 쓰지 않는다.** Draft → Ready는 사람이
- **Jira 상태를 옮기지 않는다**
- **머지하지 않는다**
