# PR 리뷰 (pr-review)

**분리 실행**과 **Pn 등급**이 이 스킬의 전부다. 사람 리뷰를 대체하는 게 아니라, 사람이 보기 전에 걸러내는 1차 통과다.

## 규칙 — 이걸 어기면 스킬이 무의미해진다

- **diff를 이 세션에서 읽지 않는다.** 리뷰 범위(브랜치명 / PR 번호)만 확정해서 `pr-reviewer` 서브에이전트에 넘긴다.
- 방금 그 코드를 내가 짰더라도 **구두로 의도를 설명하지 않는다.** 설명하는 순간 리뷰가 변호가 된다.
  문맥은 말이 아니라 **PR 본문**에 있어야 한다. 본문에 없어서 리뷰어가 이해 못 했다면, 그건 리뷰어의 문제가 아니라 PR의 문제다. (저 문맥 원칙)
- 리뷰 결과는 **등급이 정한 대로 처리한다.** 무엇을 고칠지 고르지 않는다 — P1·P2는 반영하고 다시 리뷰를 돌린다(6절).
  **골라내기를 막는 것은 "사람이 정한다"가 아니라 "규칙이 정해져 있다"이다.**
- **결과를 손에 쥔 채 올릴지 묻지 않는다.** 검증만 하고 전부 등록한 뒤 보고한다.
  잘못 올린 코멘트는 지울 수 있다 — **거르는 것보다 지우는 게 낫다.**

## 0. Preflight — `gh`가 PATH에 있는지 본다

```bash
command -v gh >/dev/null || export PATH="/opt/homebrew/bin:/usr/local/bin:$PATH"
command -v gh >/dev/null || echo "GH_MISSING"
```

없으면 **여기서 멈추고 사람에게 설치를 요청한다.** `git diff`만으로 진행하지 않는다 —
PR 본문을 못 읽는 리뷰는 문맥이 비었다는 지적만 잔뜩 만들어낸다.

## 1. 범위 확정

```bash
git rev-parse --show-toplevel
git branch --show-current
gh pr view --json number,title,url,isDraft 2>/dev/null
git fetch origin dev
git diff origin/dev...HEAD --stat
```

- 인자로 PR 번호가 왔으면 그것: `gh pr diff <번호>`
- 아니고 현재 브랜치에 PR이 있으면 그 PR
- PR이 없으면 `git diff origin/dev...HEAD`

`--stat`으로 **어느 쪽 변경인지**(웹 코드 / 서버리스 `api/`·`server/` / 문서·설정)도 함께 확정한다.

**리뷰 단계도 판정한다.**

| 단계 | 조건 | 무엇을 보나 |
| --- | --- | --- |
| **1차 (작업 계획)** | `isDraft: true` + `Project/` 코드 변경 없음 | Spec이 구현 가능한가, 범위가 맞는가 |
| **2차 (결과물)** | 그 외 전부 | 만들어진 결과 전체 |

## 2. 서브에이전트 호출

`Agent` 도구를 `subagent_type: "pr-reviewer"`로 호출한다. 프롬프트엔 **범위만** 담는다.

```
리뷰 대상: PR #27 (gh pr diff 27)
저장소 루트: <위에서 확인한 toplevel 경로>
변경 범위: 웹 · 서버리스 · 문서 중 해당하는 것
리뷰 단계: 2차(결과물)      ← 또는 1차(작업 계획)
```

무엇을 왜 만들었는지, 어디를 봐달라는지 **적지 않는다.**

에이전트는 **JSON 하나**로 답한다 (`verdict` · `scale` · `findings[]`). 형식은 `.claude/agents/pr-reviewer.md`에 있다.

## 3. 결과 받기 — 파싱하고 검증한다

### 파싱

코드펜스나 머리말이 섞여 올 수 있다. 감싸고 있는 코드펜스를 벗기고 **첫 `{`부터 마지막 `}`까지**를 취한다.
그래도 JSON이 아니면 **리뷰를 다시 돌리지 않는다.** `SendMessage`로 같은 에이전트에게 "방금 판단을 형식만 JSON으로 다시 달라"고 요청한다.
`{"error": ...}`가 오면 그 사유를 그대로 전하고 멈춘다.

### 검증 — GitHub에 올리기 전에 여기서 거른다

| 확인 | 어긋나면 |
| --- | --- |
| `grade`가 `P1`~`P5`인가 | 그 건을 **P3으로 보고 정정 사실을 보고에 적는다** |
| `anchor`가 `line`·`file`·`body`인가 | `body`로 강등 |
| `line` 앵커에 `path`·`line`이 있는가 | `body`로 강등 |
| `start_line`이 있으면 `line`보다 **작은가** | **`start_line`만 버리고 단일 줄로.** 강등하지 않는다 |
| `file` 앵커에 `path`가 있는가 | `body`로 강등 |
| `verdict`가 P1 유무와 맞는가 | P1 유무를 따른다. **등급이 기준이다** |

**강등은 하되 지적을 버리지는 않는다.**

### 등급은 손대지 않는다

형식 정정 말고 내용에 따른 등급 조정은 하지 않는다.

| 등급 | 의미 | 다음 행동 |
| --- | --- | --- |
| **P1** | 꼭 반영 | 고치거나, 못 고치는 합리적 근거를 남긴다 |
| **P2** | 적극 고려 | 수용하거나 근거를 들어 반론한다 |
| **P3** | 웬만하면 | 수용하거나, **미룰 거면 Jira 티켓으로 남긴다** |
| **P4** | 반영해도 안 해도 | 무시해도 된다 |
| **P5** | 사소한 의견 | 무시해도 된다 |

**머지를 막는 것은 P1뿐이다.** `findings`가 빈 배열로 와도 **그대로 4단계로 간다.**

## 4. GitHub에 올리기

에이전트가 준 JSON을 그대로 올린다. **여기서 diff를 읽지 않는다.**

### 묻지 않고 바로 올린다

3단계 검증을 통과했으면 **확인 없이 등록한다.** 되돌릴 수 있다 — 개별 인라인 코멘트는 지워진다.

```bash
gh api repos/{owner}/{repo}/pulls/comments/<코멘트_id> --method DELETE
```

중복 정리도 하지 않는다. 등록 후 총 몇 건이 됐는지만 보고에 적는다.

```bash
ME=$(gh api user --jq .login)
gh api repos/{owner}/{repo}/pulls/<번호>/reviews --jq "[.[] | select(.user.login == \"$ME\")] | length"
```

### 지적이 0건이어도 등록한다

`findings`가 `[]`로 와도 **본문 전용 리뷰를 하나 등록한다.** 건너뛰면 "리뷰를 돌렸는데 깨끗했던 것"과
"아예 안 돌린 것"이 똑같아 보인다. 본문은 아래 머리말에 한 줄을 더한다.

```markdown
**지적 없음.** P1~P5에 해당하는 것을 찾지 못했습니다.
```

이 경로에서는 `comments[]`를 넣지 않는다(빈 배열도). **PR이 없는 브랜치는 등록할 대상이 없다** — 5단계 보고만 한다.

### 리뷰 본문 머리말 — 누가 썼고 무엇을 봤는지 밝힌다

```markdown
> 이 리뷰는 **Claude Code가 작성**했습니다. 사람 리뷰를 대체하지 않는 1차 통과입니다.

## 판정: <verdict>

- 리뷰 단계: <1차(작업 계획) | 2차(결과물)>
- 변경 범위: <웹 | 서버리스 | 웹+서버리스 | 문서·설정>
- 대상 커밋: `<headRefOid 앞 7자리>`
- 규모: <에이전트가 준 scale 문자열>
```

> `rules-ci.yml`의 AI 서명 검사는 **커밋 메시지와 PR 본문만** 본다. 리뷰 코멘트는 대상이 아니므로
> 이 고지는 CI에 걸리지 않는다. 단, **PR 본문에는 쓰지 마라.**

### event는 항상 COMMENT

GitHub은 **PR 작성자가 자기 PR을 승인하거나 변경요청하는 것을 막는다**(422). `verdict`는 본문에 글로 적고,
event는 항상 `COMMENT`. **머지를 막는 것은 사람이 한다.**

### anchor에 따라 세 갈래로 나눈다

| `anchor` | 어디에 | 엔드포인트 |
| --- | --- | --- |
| `line` | 그 코드 줄 | `pulls/{n}/reviews` 의 `comments[]` |
| `file` | 그 파일 전체 | `pulls/{n}/comments` + `subject_type: "file"` |
| `body` | 리뷰 본문 | `pulls/{n}/reviews` 의 `body` |

`subject_type`은 `reviews`의 `comments[]`에서 **거절된다**(422). 파일 단위는 반드시 별도 엔드포인트다.
**`file` 지적이 하나라도 있으면 PR에 리뷰가 두 개 생긴다**(껍데기 리뷰). 5단계 보고에 적는다.

### 순서

1. 커밋 SHA — `gh pr view <번호> --json headRefOid -q .headRefOid`
2. 페이로드는 **파일로 만들어 `--input`으로.** 한글과 마크다운이 셸 따옴표에서 깨진다
3. `line` + `body` 지적 → 리뷰 하나로 POST
4. `file` 지적 → 건별로 POST

**페이로드는 저장소 밖에, PR 번호로 고정한 경로에 쓴다.** `mktemp -d`는 쓰지 않는다 — 셸 변수는 Bash 호출이 바뀌면 사라진다.

```bash
WORK="${TMPDIR:-/tmp}/pr-review-<번호>"
mkdir -p "$WORK"
gh api repos/{owner}/{repo}/pulls/<번호>/reviews  --method POST --input "$WORK/review.json"
gh api repos/{owner}/{repo}/pulls/<번호>/comments --method POST --input "$WORK/file-1.json"
```

끝나면 `rm -rf "$WORK"`.

`review.json`:

```json
{"commit_id": "<sha>", "event": "COMMENT", "body": "> 이 리뷰는 **Claude Code가 작성**했습니다. ...\n\n## 판정: Request changes\n\n- 리뷰 단계: 2차(결과물)\n- 변경 범위: 웹\n- 대상 커밋: `a1b2c3d`\n- 규모: 312줄 ...",
 "comments": [{"path": "Project/src/apply/...", "start_line": 38, "start_side": "RIGHT",
               "line": 42, "side": "RIGHT", "body": "**P1** ..."}]}
```

`file-1.json` — `commit_id` 필수:

```json
{"commit_id": "<sha>", "path": "Project/src/...", "subject_type": "file", "body": "**P2** ..."}
```

`line-1.json` — **폴백에서만 쓴다.** `subject_type`을 **넣지 않는다** — 넣으면 422가 아니라 200이 오고
위치만 조용히 사라진다. `commit_id`는 건마다 필요하다.

```json
{"commit_id": "<sha>", "path": "Project/src/...", "start_line": 38, "start_side": "RIGHT",
 "line": 42, "side": "RIGHT", "body": "**P1** ..."}
```

### 422가 나면 — 2단 폴백

`comments[]` 중 **하나라도 앵커가 틀리면 리뷰 전체가 422로 죽고**, GitHub은 어느 것인지 알려주지 않는다.

1. **1차** — `line` 코멘트를 전부 담아 `reviews`로 POST. 성공하면 끝
2. **2차 (422)** — `comments[]`를 **비우고** 본문만 리뷰로 올린 뒤, `line` 지적을 `pulls/{n}/comments`에
   **건별로** POST(`line-1.json`). 틀린 앵커만 개별적으로 실패한다
3. 그래도 실패한 지적은 **버리지 말고** 리뷰 본문에 추가한다(`PUT pulls/{n}/reviews/{id}`).
   보고에 **"인라인으로 못 붙인 N건"** 명시

**조용히 빼먹는 것이 최악이다.**

### 잘못 올렸다면

| 대상 | 지우기 | 고치기 |
| --- | --- | --- |
| **리뷰 객체** | ❌ 삭제도 dismiss도 안 됨 | `PUT pulls/{n}/reviews/{id}` 로 본문만 |
| **개별 인라인 코멘트** | ✅ `DELETE pulls/comments/{id}` | `PATCH pulls/comments/{id}` |

### 등록했으면 6절 반영으로 간다

등록이 끝나면 **바로 보고하지 않는다.** 6절로 가서 등급대로 반영하고, 루프가 끝난 뒤 5절 보고를 한 번 한다.
**지적이 0건이면 곧장 5절로 간다.**

## 5. 보고 — 루프가 끝난 뒤 마지막에 한다

**이미 등록되고 반영까지 끝난 다음에 하는 보고다.** "올릴까요"가 아니라 "올렸습니다"로 쓴다.

```
리뷰 등록 완료 · PR #27 · 판정: Request changes
https://github.com/.../pull/27#pullrequestreview-XXXX

P1 1건 — 머지 전 필수
  ApplyRail.tsx:42  진료비가 숫자 문자열이 아니면 NaN원 → 화면에 그대로 노출

P2 2건 — 고려
  state.ts:15  step 6에서 goto가 막히지 않음 → 접수 후 되돌아가 중복 접수
  PR 본문에 390 스크린샷 없음 (3장 중 1장 누락)

P3 이하 3건 — 접어둠 (필요하면 펼쳐줄게)

등록 내역: 코드 줄 3건 · 파일 2건 · 본문 4건 · 이 PR의 내 리뷰 총 1건
```

지적이 0건이어도 형식은 똑같이 "등록 완료"로 시작한다. **리뷰 링크는 맨 위에.**

### 루프가 돌았으면 그 내역이 보고의 중심이다

```
리뷰·반영 완료 · PR #27 · 최종 판정: Comment
https://github.com/.../pull/27#pullrequestreview-XXXX

반영 2회 — 1회차 P1 1건·P2 2건 / 2회차 P2 1건 (커밋 a1b2c3d, e4f5g6h)

⚠️ 재리뷰에서 또 지적된 것 1건
  state.ts:15  step 6 goto — 1회차에 고쳤는데 2회차에 다시 P2

반영하지 않고 넘어간 것 1건
  analytics.ts:88  구조를 바꿔야 해서 이 PR 범위 밖 — 스레드에 이유 남김

P3 이하 3건 — 접어둠
```

- **재리뷰에서 또 지적된 것**은 반드시 맨 위에
- **반영하지 않고 넘어간 것**과 그 이유
- 종료 사유 — 깨끗해져서, 2회 상한, 같은 지적 반복 중 무엇인가
- 폴백이 돌았는가 · 강등한 지적이 있는가 · 껍데기 리뷰가 생겼는가

## 6. 반영 — 등급이 정한 대로 하고, 다시 돌린다

**사람에게 묻지 않고 바로 반영한다.**

| 등급 | 처리 |
| --- | --- |
| **P1** | **반영 → 재리뷰** |
| **P2** | **반영 → 재리뷰** |
| **P3** | 반영하지 않는다. 보고만. 미룰 거면 Jira 티켓(`mcp__atlassian__createJiraIssue`) |
| **P4·P5** | 반영하지 않는다. 보고만 |

**등급을 손대지 않는다.** 반영할 수 없다고 판단한 지적은 **그 스레드에 이유를 적고** 넘어간다. 침묵하면 반영된 것처럼 보인다.

### 재리뷰는 등록 전에 묻는다 ⏸

**한 PR에 리뷰를 두 번째로 등록하기 전에는 멈추고 사람에게 확인받는다.** 반영(코드 수정·커밋·스레드 답글)은
자동이다 — 멈추는 것은 **리뷰 등록**이다. 리뷰가 쌓이면 PR이 읽기 어려워진다.
한 줄로 묻는다 — 지금까지 등록된 리뷰 수 · 이번 재리뷰가 볼 것(반영 커밋 몇 건). 사람이 "됐다"고 하면 재리뷰 없이 5절로 간다.

### 종료 조건

- **반영은 최대 2회**(리뷰는 최대 3회). 넘으면 남은 지적을 안고 멈춰서 보고한다
- **같은 지적이 두 번 나오면 즉시 멈춘다**
- **반영 커밋도 커밋 게이트(`.claude/hooks/verify-web.sh`)를 통과해야 한다.** 루프가 스스로 망가지는 것을 그 게이트가 잡는다

### 1차 리뷰(작업 계획)에는 적용하지 않는다

문서 단계의 지적은 **자동으로 고치지 않는다.** 스펙을 기계가 고치면 사람이 승인한 계획이 조용히 달라진다. 보고만 하고 사람이 정한다.

### 반영 내역은 해당 스레드에 답글로만 단다

```bash
gh api repos/{owner}/{repo}/pulls/<번호>/comments/<코멘트_id>/replies \
  --method POST --input <본문파일>
```
